## Safe limits and recommendation

For a prospective controlled **resource** pilot, retain one guide and one thread, the existing search settings, a hard **64 GiB aggregate job/process-tree memory cap**, a **two-hour wall limit**, a verified scratch filesystem with at least **60 GB initially free** beyond the persistent approximately 14.54 GB bundle, an enforceable aggregate scratch/output quota, monitoring, and no automatic retry. These are proposed safety limits, not measured requirements or a prediction of success. A timeout or resource stop must leave an incomplete result. The present script and previous bounded measurements do not establish worst-case assembly-wide memory, runtime, search sensitivity or safety on a shared host. A per-process `ulimit` or observed free RAM is not a substitute for an enforced process-tree cap. `timeout` alone is not evidence that all descendants are constrained or killed.

**Recommendation:** do not run on any of these nodes yet. Prefer assessing `octopus10` first because its scheduler snapshot shows more free memory than any responding tux node and no allocated CPUs. Its actual `MemAvailable`, unmanaged workloads, NFS paths, dependencies, quotas and enforceable job-wide memory limit remain unknown. Consider `tux07` only if a permitted read-only node check confirms adequate `MemAvailable` and safe controls; do not assume its low `FreeMem` either proves or disproves usable headroom. Do not place the pilot on tux05/06 while the 700 GiB jobs are active or on tux08/09 while down. If the administrator recommends a different node or partition with actual enforcement, that verified configuration takes priority over this snapshot.

Ask the administrator which node/partition enforces 64 GiB across all descendants, how its cgroup and OOM status can be verified, whether scratch quotas and the imported bundle are accessible from that node, and how to prevent automatic Slurm requeue. The observed octopus06 diagnostic had `Requeue=1`; an eventual pilot submission must explicitly ensure no automatic requeue and verify the resulting job configuration. A tux-specific read-only diagnostic could resolve access and current node observations only with the user's approval and the appropriate allocation/authorization. The prepared diagnostic from the [HPC resolution report](../pilot_preparation/HPC_RESOLUTION_2026-11-06.md) is currently targeted at `workers` and must be reviewed before using it elsewhere. No diagnostic is submitted by this report.

A successful future pilot would measure resource consumption and audit emitted-site eligibility for one guide; it would not prove genome-wide sensitivity. No production binary, search algorithm, index, default or branch was changed by this assessment.
