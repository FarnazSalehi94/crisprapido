# Columba index and prototype limits

This audit concerns the locally recorded Columba checkout `edcc7ce2a1e28ded6784a44afbd8b9348a4805ad` and the prototype built by [build.sh](../build.sh). The checked-out source is tracked-clean but the runtime build is untracked; this does not prove a reproducible source-to-binary build. No chromosome-scale or whole-genome index was built in this study.

* `src/definitions.h:69–75` defines Columba `length_t` as `uint32_t` under `THIRTY_TWO`; the prototype explicitly compiles with `-DTHIRTY_TWO`, alphabet 5, and uses `FMIndex(..., 4, ...)` with suffix-array sampling 4. Suffix-array intervals and positions use `length_t`. `src/indexinterface.cpp` checks the recorded `.meta` word width and flavor against the runtime. The local Python [index_check.py](../validation/index_check.py) also assumes little-endian 32-bit `.txt.bin` length and `.pos` entries and 64-bit serialized name lengths. It does not support a 64-bit index simply because Columba can be compiled for one. The manifest pins the complete component set, but is not a signed authenticity proof.
* In `src/buildindex.cpp:395–415`, `checkTextSize` rejects text larger than `uint32_t::MAX` when built 32-bit. `buildindex.cpp:650–672` concatenates contigs and appends the terminal `$` before the final check. For ordinary FASTA without an existing sentinel, the **representational upper bound** is therefore 4,294,967,294 reference bases in total across all contigs, plus one sentinel. There is no separate larger per-contig capacity: any one contig is constrained by the same total and 32-bit start/end offsets in `.pos`. This is a theoretical maximum, not a tested safe size; arithmetic near the boundary, index library assumptions and memory require further audit. A missing sentinel or a wrapped count cannot safely be accepted by inference from that number alone.
* `src/buildindex.cpp:479–510` uses a signed 32-bit `libsais` call only at text length up to `INT32_MAX` (2,147,483,647). Above that, the **32-bit** build uses `libsais64` with an `int64_t` suffix-array vector, then reserves and fills a `uint32_t` vector while the 64-bit vector remains alive. Those two arrays alone can require approximately 12 bytes per indexed symbol simultaneously, excluding input strings, BWT, allocator and library workspace. A 3-billion-symbol build therefore implies roughly 36 GB (decimal) for these two arrays alone; this is an analytical lower bound for that phase, not a measured peak or safe allocation estimate.
* Columba's CMake and README offer `THIRTY_TWO=OFF`/64-bit builds and an alternate 64-bit suffix-array path, but every prototype, checker, binder, serialized index and runtime library must use a compatible format. A change of macro alone is not a supported migration. Design versioned width/endian/format metadata, rebuild rather than reinterpret 32-bit artifacts, audit all operations and address calculations for overflow, test SA range and contig boundaries at width transitions, and validate the builder and consumer together. The helper's `.sna` interpretation also depends on the builder's serialized `size_t` width.
* In [poc.cpp](../poc.cpp), record offsets and output coordinates use `size_t`; `idx.findSA` and SA range iteration use Columba `length_t`. Search depths, guide index and edit counters use signed `int`, and the search-state counter is signed `long long`. No general arbitrary-length guide or counter-overflow guarantee is established. The in-memory `map` retains one representative per discovered PAM anchor, recursive path strings are copied, and suffix-array locate iterates occurrences. Large repeat intervals or many anchors can therefore be expensive even when recursion depth is guide-length bounded.
* `FMIndex::fromFiles` loads `.txt.bin` into a full text string, plus BWT representations and sparse SA. The prototype separately loads the entire FASTA and stores output hits. The Python binding verifier constructs additional full reference and text copies; the runner copies all components to temporary storage, buffers native stdout and reconstructs all reference records, while Rust also buffers the returned output. These are multiple concurrent allocations/processes; measured 3 Mb RSS cannot be extrapolated linearly into a safe chromosome/genome peak. Output volume and many guides add unbounded-by-reference memory pressure.

Chromosome-sized references are below the *nominal* coordinate cap and the 3 Mb experiment is far below both the 32-bit and signed suffix-array thresholds. That supports only the bounded 3 Mb experiment, not a demonstrated safe chromosome-sized run. A complete human reference might fit the nominal 32-bit total depending on the exact FASTA and alt/decoy content, but the memory-heavy >2^31 builder path, 32-bit boundary safety, N substitution provenance, temporary copies, output buffering, aggregate memory and exact input composition must be assessed. General support for larger references or concatenated genomes requires a tested 64-bit implementation or carefully validated sharding with PAM-aware overlap and anchor deduplication.
