# PAM-anchored prototype: broader validation and bounded benchmarks

2026-11-04. **Recommendation: do not integrate yet.** The prototype passed the resolved-reference bounded tests and agreed with the current implementation on two 2 Mb samples. It missed 75 independently expected sites when the reference target contained `N`; the existing implementation recovered them. The benchmark results show lower observed elapsed time for this prototype under a narrower output contract, but do not establish an isolated, fully equivalent search speedup.

## Correctness

We selected new, nonoverlapping 1 kb extracts from each of the existing 2 Mb CHM13 chr1/chr9 and GRCh38 chr1/chr9 regions (parent offsets 400,000, 13,000, 420,000 and 1,865,000 respectively); see [panel metadata](results/panel.json) for coordinates, sequence hashes and precise edit positions. The two chr9 blocks were selected as repeat-enriched using a within-parent, nonoverlapping 20-mer proxy: 30/50 sampled 20-mers in the CHM13 block and 21/50 in the GRCh38 block recur elsewhere in their respective 2 Mb parents. This is a repeat proxy, not formal repeat annotation. For each extract and strand, eight 20-mer guides were derived from a strict PAM, including exact, five mismatches, one- and two-base insertions and deletions, a two-base guide insertion plus three mismatches, and a two-base reference insertion plus five mismatches. All 64 intended edit classes were independently confirmed at their source anchors; for guide insertion of size two, five mismatches cannot meet the 15-match requirement at f=.75. All guides were searched across all extracts. The four unmodified regions contain resolved A/C/G/T. Four additional copies have deliberately introduced Ns, including inside the original target at each strand's design PAM: these are engineered stress cases, not naturally observed human N locations. Complete `ref.fa`, guides and oracle are retained in [results](results/).

The independent oracle enumerates every complete A/C/G/T NGG, both orientations, lengths 18–22 and every placement of zero or one contiguous 1–2-base gap, then directly counts matches and mismatches, treating a reference N as a mismatch in aligned columns. N in a complete PAM is ineligible. This matches the current implementation's observed treatment of this panel, not a claim about all ambiguity codes or all CLI modes. Results use zero-based PAM start in the oracle and convert the prototype's minus boundary by three. Independent replay audits the CIGARs, PAM and limits of **every emitted row** in both methods; it does not require identical alternative CIGARs. The oracle includes 36 pairs of nearby anchors at most three bases apart and 96 anchor/category memberships permitting five mismatches plus a two-base reference bulge; categories overlap.

The [discrepancy investigation](results/n-investigation.json) enumerates all eligible alternatives at each missed anchor: all 75 have at least one eligible alignment spanning N and **none** has an eligible resolved-target alternative. The prototype explicitly rejects every target span containing a non-ACGT base, including an N inside a DNA gap, whereas the baseline emits valid N-containing alignments (for example `15=1X4=` for an engineered target). Thus these are genuine omissions relative to the current eligibility policy, not coordinate or tie differences. Index substitution of ambiguous bases introduces a second potential source of missed paths, so simply removing the rejection would not establish completeness. No extra anchors or duplicates were observed.

A separately generated deterministic randomized resolved-reference set (seed 44751; 16 small contigs and 16 guides) yielded **29/29** oracle anchors, zero extras or duplicates. The original 8 kb panel remained **204/204** after adding timing instrumentation. The earlier difficult fixtures and eight PAM wildcard/strand cases also passed again. These bounded tests are not a whole-genome completeness proof. The retained 2 Mb comparisons below check agreement and emitted-row validity, not exhaustive recall.

## Search-state analysis

For resolved 20-base guides and strict NGG, assuming the supplied index really represents the supplied contigs and resources suffice, the four seeds enumerate all possible resolved PAM first bases, and paired FM intervals extend the remaining guide on the appropriate side. Empty-interval pruning only discards strings absent from the indexed text. Mismatch count pruning is monotonic. The `matches + remaining guide bases` test is an optimistic upper bound and cannot remove a path that can still reach f=.75. The DFS tracks a gap as open or closed and permits at most one contiguous insertion **or** deletion, up to configured length; it enumerates alternative placements instead of retaining only the edit-distance optimum. SA interval expansion preserves repetitions; contig-end checks reject paths spanning concatenated records. Strand reversal and guide-oriented CIGAR reconstruction passed the bounded oracles. PAM bases use exact transitions and no guide edit budget. Multiple valid traces collapse only after eligibility into one anchor representative; this does not guarantee WFA's preferred CIGAR or score.

These statements are an inspection argument, not a formal proof. The implementation is limited to strict NGG, resolved guides and resolved target spans, one gap event, 32-bit vanilla index with SA sampling four, nonempty target and the supplied match-fraction rule. It does not support requested non-GG PAMs, noncanonical/unavailable PAM mode, `--no-filter`, multiple gap events, full CRISPRapido CLI behavior or CFD. It assumes FASTA names, order and sequence match the index; the standalone checker is not enforced inside the POC. A gap containing N, target N as a mismatch, and arbitrary ambiguity handling need explicit design and test. Check invalid parameters, floating thresholds, long sequences/overflow, extreme repeats, boundary-crossing PAMs, equivalent traces, randomized indels, source-to-binary reproducibility and score/representative policy before any integration. Columba's own index may substitute ambiguous bases and thus lose the original identity; recovery requires a sound ambiguity strategy rather than a local output-filter change.

The original release manifest records [Columba](https://github.com/biointec/columba) checkout `edcc7ce2a1e28ded6784a44afbd8b9348a4805ad`; the release wrapper invokes VANILLA 2.0.3. The release binary and the recovered build executable have identical SHA256 `7e44974c81dad4943292fa64a71e54073908b4909ce327480464d769322c40d1`. Tracked source and archive, wrapper, library, prototype and baseline hashes are in [provenance.json](results/provenance.json). The checkout has no tracked modifications, but its build directory is untracked and no source-to-binary attestation exists: the recorded source revision is strong provenance evidence, not proof of the exact compilation inputs. A fresh HTTPS `ls-remote` with certificate verification and the system CA returned no refs; no TLS bypass was used, so current upstream main and an exact diff remain unresolved.

The [index checker](index_check.py) compares FASTA names and order with `.sna`, lengths and offsets with `.pos`, and every A/C/G/T base with the concatenated `.txt.bin`; it checks the sentinel and reports ambiguous positions which cannot be checked because the builder replaces them. Unit tests cover changed bases, renamed contigs and incorrect boundaries. The eight-contig panel has 40 ambiguous positions and zero resolved-base disagreements; this is not proof that the Ns had any particular original indexed character, nor by itself proof that BWT or SA components are intact. For both resolved 2 Mb benchmark references, a fresh scratch index built with the recovered vanilla builder had byte-identical `bwt`, `brt`, `rev.brt`, `sa.4`, `sa.bv.4`, `pos`, `sna`, `txt.bin`, `cct` and `meta` components to the prebuilt indexes. This is stronger evidence for these two pairs, conditional on the builder, and does not generalize to randomly replaced ambiguous bases.

## Performance

Runs were sequential and single-threaded on the same `octopus01` AMD EPYC 7402P host, using prebuilt indexes and identical guide/reference and strict m5/b1/z2/f.75 constraints. Two repetitions per case, index build excluded. The baseline is a separately built instrumentation copy of the existing branch's source, using `scripts/release_validation/make_profile_build.py --no-cache`; its 8 kb PAF is byte-identical to the retained uninstrumented baseline. Timing guards add overhead. The prototype timer covers DFS, locating and its reference/CIGAR checks but excludes initial FASTA/index loading and TSV output. End-to-end wall times include input and output. GNU time RSS is the maximum of individual processes, not combined parent-plus-child RSS. These are finite samples, not whole-genome forecasts.

| Original 8 kb | 96 | 0.70, 0.70 | 0.699, 0.701 | 8,313,485 | 4,284, 4,296 | 13.74, 13.74 | 35,436, 35,392 | 204 |
| CHM13 chr1 2 Mb | 1 | 0.65, 0.65 | 0.639, 0.642 | 8,406,922 | 13,844, 14,076 | 29.47, 29.23 | 68,412, 69,676 | 10 |
| GRCh38 chr9 2 Mb | 1 | 0.60, 0.60 | 0.586, 0.587 | 7,616,819 | 14,312, 14,132 | 29.98, 29.92 | 69,340, 68,708 | 23 |

The two 2 Mb input windows were existing CHM13 chr1:100000001–102000000 and GRCh38 chr9:30000001–32000000, using the same ELMOD2 guide; every emitted alignment was independently replayed, and sets matched in each repetition. No exhaustive 2 Mb oracle was run. Full measurement summaries and hash-checked index data are in [results](results/). The existing instrumented baseline's measured CFD work was about 0.0006 s per 8 kb run and at most 0.0001 s per 2 Mb run; WFA calls consumed about 10.25–10.30 s and 22.04–22.58 s respectively. Columba subprocess waits were about 0.27–0.29 s and 0.47–0.49 s respectively. These phase timers do **not** completely isolate search from I/O: Columba wait includes process startup and SAM generation, other verification work and output are separate, and some timers may overlap. The prototype does not compute CFD or reproduce baseline representative selection. Therefore its shorter end-to-end wall time here is an encouraging observation for these cases, not a calibrated same-work speed ratio. A direct comparison of just Columba-wait and POC search is also invalid because Columba generates a candidate superset and the POC produces eligible anchors.

## Reproduction and next steps

`make_panel.py SOURCE_SCALING SCRATCH_DIR` creates the real-derived and engineered-N panel, direct oracle and designs. Build a fresh vanilla index with `columba_build -r SCRATCH_DIR/index -f SCRATCH_DIR/ref.fa`; run `index_check.py`, then the prototype and the original pipeline with the constraints above. `compare.py SCRATCH_DIR` independently audits and reports exact keys; `investigate_n.py SCRATCH_DIR` explains prototype misses. The retained results can be rechecked directly with those two scripts. `randomized.py` creates the separate resolved differential test. `benchmark.py --help` documents the bounded repeated runner; use a wrapper if the local runtime requires an explicit loader. `check_rebuild.sh` compares a fresh index with an existing prefix. These scripts do not write to production binaries or frozen branches.

Resolve N semantics and index traversal first, enforce index/reference identity, broaden exhaustive randomized and repeat/edge testing, compare representative selection, and develop equivalent search-only instrumentation before proposing integration. No defaults, production executable, frozen branch, or main branch were changed; no whole-genome/pangenome experiment, CFD-guided pruning or CRISPR-Bulge integration was performed.
