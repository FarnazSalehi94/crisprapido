# HG00735_pat bounded large-coordinate probes

2026-11-05. Bounded exact probes against the imported HG00735_pat index passed on both strands near the beginning, on either side of `2^31`, at contig boundaries and near the end. A genuine plus-strand target containing three reference Ns was recovered with the correct anchor and three mismatches. The native probe's sampled aggregate process-group peak was **13.57 GiB** with index and full reference loaded. This is useful targeted evidence, not proof of whole-assembly mismatch/bulge recall or a measurement of the full CLI. No whole-assembly guide search was run.

## Method and scope

[select_probes.py](select_probes.py) reads the source `.fai` only after checking its SHA256 against the imported bundle's evidence, then uses indexed random access to small windows of the exact imported plain FASTA and `.txt.bin`. It selects strict PAM-containing 23-mers at assembly ends, on either side of `2^31`, and within 1 kb of a contig boundary. It also selects patterns that cross a contig boundary: such concatenated indexed strings may exist, but the prototype must not report them as a contig-local alignment. N examples were discovered by a bounded scan of at most the first 1 GB of FASTA bytes for N-block starts, followed by 20 kb window inspection around those starts; gap ends outside those windows were not systematically examined. This was not a search for a guide or an exhaustive genome scan. The scan did not find a natural minus-strand N-overlap example or natural PAM-N examples under its bounds; those are not claimed as covered.

[verify_cases.py](verify_cases.py) independently retrieves the selected 23-base windows from the original BGZF FASTA using `samtools faidx`, including both pieces of crossing-boundary controls. It compares those short windows to the selected plain-reference bytes, checks `.pos` offsets, independently reads the corresponding indexed text, reorients plus/minus sequence, and recomputes guide mismatches and strict PAM eligibility. The original compressed file's full SHA256 was verified during import, not rehashed during this bounded sampling. The stage itself is checked through the native binding verifier before and after the probe.

[build_probe.py](build_probe.py) builds a separate research executable from the **unchanged prototype source**, using its `FMIndex` primitives, direction handling, `findSA`, FASTA loader and `Search::emit` implementation. Each case performs a single exact 23-base indexed lookup in the appropriate direction; it checks the expected global suffix-array coordinate, contig assignment, anchor, reference sequence and replayed mismatch count. The main run expands no SA interval wider than 64 entries; wider intervals are reported as skips, not incorrectly classified as absent. A separate follow-up uses a 128-entry cap on one exact near-end pattern with a 66-entry interval. There is no edit-distance traversal or whole-assembly guide search. The small fixture validates both directions and six in-memory N/PAM controls before the large probe. For the large probe, the N-at-target, N-at-PAM-wildcard and N-at-required-G controls replace one base **only in the probe's in-memory reference**, restore it after each control, and do not modify the staged FASTA. These negative controls test `Search::emit` behavior but are not naturally occurring HG00735 observations.

The probe verifies the full reference/index binding before loading and after lookups. The ordinary mode/unsigned manifest assumptions and same-user adversarial race documented in the import report still apply. Results from an incomplete run or a failed postcheck are not accepted. The original HPRC index files and the staged bundle are not modified.

## Coordinate and N results

The [main run](results/main-summary.json) selected **51** exact patterns. An independent reader compared them against **53** short windows of the original BGZF reference and the corresponding indexed text; crossing patterns need two source windows. **37** case rows completed under the 64-entry cap, including both plus/minus contig-crossing cases, which were located in the concatenated text and correctly rejected by `Search::emit`. **14** intervals were skipped, with widths 66–18,756; a skip is not evidence of absence. Three selected patterns were repeated under different location labels, so the 37 completed rows represent 34 distinct `(global position, strand)` pairs. The [one-case follow-up](results/followup-summary.json) revisited one previously skipped plus-strand near-end pattern under a predeclared 128-entry cap, located all necessary candidates in its 66-entry interval, and found the expected anchor. Thus 38 of the original 51 selected rows were eventually checked and 13 remain untested due to the smaller cap; the 38 rows represent 35 distinct position/strand pairs. Both runs passed full binding checks before and after.

The genuine plus-strand N case at global offset 978,574,377 has source-oriented sequence `NNNAAGCACACCTGCAGATAAGG`; the corresponding indexed sequence begins `CAT` instead of `NNN`. The exact indexed pattern was located at the expected global position, reference replay recovered the original Ns, strict PAM `AGG` and local anchor 9,138,278, and the prototype counted **three mismatches**. This does not prove general N-aware traversal completeness. Six in-memory target-N controls (three per strand) were emitted with one mismatch; twelve in-memory PAM-N controls were rejected, covering both N in the wildcard position and N in a required G on both strands. These controls are synthetic changes to the loaded copy of the reference and were restored before post-verification. The bounded N-block-start windows contained no natural minus-strand N target or natural PAM-N example selected by this method; those cases remain unproven on this assembly.

## Aggregate memory and limits

[run_probe.py](run_probe.py) sampled `/proc` process-group RSS every 100 ms, including the native executable and verifier descendants. Summed RSS can double-count shared pages and can miss peaks between samples, so these are approximate aggregate process-tree measurements, not exact unique physical memory. The primary successful run had a 900 s wall cap, 24 GiB per-process virtual-address cap and 22 GiB sampled aggregate RSS stop; no limit fired. A 300 ms hold immediately after the timed lookup retained the index and reference so the lookup phase could be sampled; it is excluded from `lookup_seconds`.

| Phase | Maximum sampled process-group RSS | Interpretation |
|---|---:|---|
| Initial binding verification | 18,156 KiB | Streaming verifier and waiting native process |
| Index loading | 11,176,020 KiB (10.66 GiB) | FM index, before full FASTA load |
| Reference loading | 14,210,580 KiB (13.55 GiB) | Index plus the full native FASTA representation |
| Targeted lookups | 14,210,580 KiB (13.55 GiB) | Resident index/reference immediately after the bounded probes; brief lookup peaks may be missed |
| Post-use verification / overall | 14,225,956 KiB (13.57 GiB) | Native process and verifier descendants |

The warm-cache index constructor took 3.70 s, native FASTA loading 18.74 s, the capped exact lookups 0.00072 s, and the complete run including two full binding checks 358.32 s. One run and 100 ms memory sampling cannot characterize a cold cache or worst-case complete-guide search. The full experimental CLI also has a Python snapshot/reference copy and output buffers that this native probe does not include. The preliminary first run stopped at its 64-entry cap on a repetitive near-end pattern and did not pass a postcheck; none of its partial results is treated as validated. Its [measurements](results/preliminary-measurements.json) remain as safety evidence.

## Reusing a verified bundle

Current integrated `-G/--guides` batch mode is already the safest available way to amortize setup: one CLI invocation takes one snapshot and performs its prescribed verification passes, launches one native process, loads one FM index and reference, and loops over all guides. That is one roughly 14.54 GB snapshot **per batch**, not per guide within the batch. Repeated single-guide invocations still repeat the full copy and verification, while a batch can increase buffered-output and hit-map memory. No production-path behavior was changed here.

The research probe in this study reused the stage directly, loaded the index once for its selected cases and checked the full binding before and after, so it did not make another 14.54 GB copy. It is not a production reuse mode: pre/post checks detect persistent changes but cannot exclude a transient same-user change and restoration between checks, and its output file is provisional until the final check. Do not substitute it for the checked adapter.

For reuse across invocations, a safe design needs a content-addressed bundle whose trusted manifest binds the exact reference, metadata and all 12 index components. Verify once during controlled import; then retain the files in a filesystem-enforced immutable snapshot/read-only namespace, or use validated open file descriptors and an equivalent content-verifying mechanism, with atomic publication and a trusted manifest root. File identity and immutable content must stay pinned for the **entire** reader lifetime; `chmod`, metadata-only checks and advisory locks alone are insufficient against a same-user writer, and an unsigned manifest can be replaced along with the data. Columba currently reopens component paths, so either the namespace must prevent substitution or the loader must be refactored to consume securely opened handles. Fail closed if the guarantee is unavailable. Retain N-containing reference bytes and contig dictionary, spool output until verification succeeds, and validate change detection, snapshot lifecycle, concurrent users and crash recovery. This is a design, not an implemented cross-process cache or a claim that the current stage is immutable.

## Readiness and reproduction

I do **not yet recommend** using a whole-assembly guide run as a correctness or completeness benchmark. These exact-pattern samples exercise `findSA` and the prototype emission path, not the full mismatch/bulge search tree, not exhaustive anchor recall, and not natural reverse-strand N-overlap or natural N-in-PAM cases. The full integrated CLI's memory and output volume on HG00735_pat are still unmeasured, the retained stage is not adversary-proof immutable storage, and search-state growth is not interruptible by an internal state cap. The existing pipeline's previously documented synthetic N-related candidate misses also mean that agreement with it alone would not prove completeness.

Before reconsidering one controlled guide, independently test high-coordinate mismatch/bulge and natural N cases on both strands, repeat boundary/PAM checks with an oracle, review the trustworthy-bundle threat model and fail-atomic output handling, and establish cgroup/temporary-storage monitoring and an explicit incomplete-result status for every timeout or limit. If such a pilot is separately authorized after that review, a conservative **starting cap**, not a demonstrated requirement or guarantee, would be one thread, a 64 GiB process-tree/cgroup memory limit, at least 60 GB free scratch **in addition to** the persistent 14.54 GB bundle, a 2-hour wall limit including pre/post verification, and an explicit output quota/watchdog. Stop and mark the run incomplete if any cap fires; do not silently truncate output or call it complete. The current adapter makes another approximately 14.54 GB snapshot per batch, and real output growth and aggregate CLI memory can exceed this probe's measurements. At inspection `/tmp` had about 37.7 GB available, below that proposed scratch headroom; a future job would need a suitable explicitly configured temporary filesystem and fresh capacity checks.

Reproduce the bounded investigation using [select_probes.py](select_probes.py), [to_tsv.py](to_tsv.py), [build_probe.py](build_probe.py), [run_probe.py](run_probe.py), [verify_cases.py](verify_cases.py) and [check_results.py](check_results.py), passing the retained stage, trusted `.fai`, original BGZF source, compatible Columba build and explicit scratch paths. The 64-entry main and 128-entry follow-up cases and their small outputs are under [results](results/); compiled executables, the full reference and indexes are not committed. [test_fixture.py](test_fixture.py) exercises both directions and six N controls on the small independent panel; [test_monitor.py](test_monitor.py) checks process-group sampling and memory-limit termination. This research probe is not a new production backend, and it does not implement region-restricted guide search, persistent bundle reuse, partitioning or CFD-guided pruning.
